## P0-1. Убрать ложный `gate_status=unavailable`

**Факт:** 6 из 6 «недоступных» гейтов прогона №2 имеют `probe_status=ok`, реальные

`signature_count_0_25 < 25` (`guard_reason=creator_history_too_short`), то есть это
**решающий отказ**, а не сбой телеметрии. Из-за этого `unavailable_share=0.4615` и пункт
«Как читать» в `SUMMARY.md` уводят читателя: он считает половину гейта слепой зоной.

Сделать:
1. Классификация: `guard_reason == creator_history_too_short` при `probe_status == ok`
   → `gate_status = fail_history` (новый класс).
   `unavailable` — **только** при `probe_status != ok` или `censored == true`.
2. `manifest.creator_gate.status_counts` — четыре класса: `pass`, `fail_history`,
   `fail_risk`, `unavailable`. `unavailable_share = unavailable / все гейты`.
3. В `SUMMARY.md` переписать «Как читать» п.1: `unavailable` — сбой пробы; `fail_history` —
   сознательный отказ по возрасту кошелька; смешивать их нельзя.
4. В блок «монеты, которые взял только A» добавить разбивку по четырём классам,
   а не по трём.

**Acceptance:** реплей прогона №2 по `decisions.csv` даёт
`pass=3, fail_history=6, fail_risk=4 (вкл. censored TESLAOPTIMUS), unavailable=0`,
`unavailable_share=0.0`.

## P0-2. Идентичность дева: fallback слишком узкий, второй счётчик не пишется

**Факт:** 10 из 13 гейтов резолвятся в `pump_curve_creator`, который у pump.fun —
одноразовая fee-обёртка (возраст **3.13 с** у Audit, **3.22 с** у haMSTR). Fallback на актора
срабатывает только при `curve_count in (0, None)`, а у свежей обёртки всегда ≥1 подпись.
Результат: haMSTR (`curve` 4 подписи / `actor` 25 подписей, реальный дев с 9803 минтами)
остался на curve → `creator_history_too_short` → B пропустил **+123.83 ₽**.

Сделать:
1. Триггеры переключения на актора (любой из):
   - текущий: `actor_valid and curve_count in (0, None) and actor_count > 0`;
   - новый: `actor_valid and actor_count is not None and actor_count >= max(3 * curve_count, curve_count + 8)`;
   - новый: `curve_wallet_age_sec < 60`.
2. Писать в `values_json` гейта для **всех** строк, включая те, где идентичность осталась curve:
   `identity_rule ∈ {curve_only, curve_zero_actor, actor_dominant, curve_too_fresh}`,
   `curve_sig_count`, `actor_sig_count`, `curve_wallet_age_sec`, `actor_wallet_age_sec`.
   Сейчас `pumpportal_event_actor_sig_count=None` в 10 из 13 строк — вопрос «а что было бы»
   по данным прогона неразрешим.
3. Не менять правило гейта (`signature_count == 25 AND ata exists AND balance > 0`) — только
   идентичность и логирование.

**Acceptance:** на данных прогона №2 haMSTR резолвится через `actor_dominant`
(4 → 25 подписей), в отчёте видны оба счётчика по каждой строке, доля `None` = 0.

## P1. Теневые армы (лог-онли, 0 ₽, 0 новых RPC)

Считаются из уже существующего тик-потока и тех же входов A. Капитал не расходуется,
слоты не занимают, на A/B не влияют, в `MAX_POSITIONS` не входят.

| арм | правило | гипотеза, которую проверяем |
|---|---|---|
| `shadow_gate_inverted` | те же входы, что A, но торгуем **только** отвергнутые B (`guard_reason != creator_guard_met`) | гейт B анти-отбирает: 17 сделок / −701.33 ₽ против 13 / −89.05 ₽ |
| `shadow_hold15` | вход A, выход не раньше 15 с (SL/TP1 работают как есть) | «5 с слишком коротко» — два выброса вышли на 4.6 и 8.4 с |
| `shadow_hold60` | то же, порог 60 с | есть ли у класса отобранных монет вторая волна |

В `ab_summary.json` — отдельные строки `shadow_*` с теми же метриками, что P0-5.1.
Каждый арм помечать `capital_rub: 0`, чтобы его нельзя было спутать с реальным портфелем.

**Acceptance:** три арма присутствуют в отчёте с n > 0; ни один не влияет на решения A/B
(проверить: `paper_fills` профилей A/B побайтово совпадают с реплеем без теневых армов).

## P2. Прогон №3: 8 часов вместо 30 минут

Конфиг — как в прогоне №2, без изменений. Длительность — **8 часов**.

Обоснование (арифметика, не вкус):
- Разница между классами `guard_met` и `history_too_short` = 34 ₽/сделку при sd ≈ 60 ₽.
- Для α=0.05 и power 0.8 нужно `2 × (1.96 + 0.84)² × (60/34)² ≈ 49` сделок **на класс**.
- `guard_met` даёт 3 сделки / 30 мин → **8.2 часа**.
- Тридцать минут доказать не могут ничего: CI среднего A в прогоне №2 = [−35.10; +30.69] ₽,
  а для значимости нуля при эффекте 2.21 ₽/сделку нужно ≈2900 сделок.

**Acceptance:** прогон доходит до 28 800 с (или корректно останавливается по внешней причине
с записанным `external_stop_reason`); `telemetry.dropped_events=0`, `write_errors=0`;
число гейтов ≥ 150, `guard_met` ≥ 45.

## Что НЕ делать в этом патче

1. Не «исправлять» `KNOWN_HOLE` (no-progress как одноразовая проверка на 5.0 с) наивным
   wall-clock таймером. В прогоне №2 haMSTR в момент 5.0 с стоил −7.8 % по `observations`
   и закрылся бы в минус вместо **+123.83 ₽**. Любое изменение этого места — отдельный арм
   и отдельный прогон.
2. Не снимать потолок `delta ≤ 2.5` (это fix #8, отдельный прогон после измерения
   `baseline_share`).
3. Не добавлять новые RPC-методы и не поднимать параллелизм: прогон №2 уложился
   в 3040 запросов / 0 ошибок / p95 84 мс, запас есть, но тратить его не на что.
4. Не смешивать P0 и P1 в один коммит: P0 — отчётность, P1 — счётчики. Если P1 поедет,
   P0 всё равно должен быть принят.
