# Промпт Кодеру: одна правка в гистограмме до старта 10a′

База — `02eab43` (`BUILD 87ef31c`). Блок §1 сделан правильно по существу: `sum(requests_per_5sec)
== requests` я перепроверил на своём смоуке (108 = 108), отчёт печатает пик с окном и
отношением, аудит больше не масштабирует, правило запуска 10b зафиксировано до старта.
**Но в самом пике есть дефект, и он ровно в той строке, ради которой делался весь блок.**

---

## 1. «Худшее 10-мин окно» может оказаться пятисекундным

`price.py`, `_window_peak()`:

```python
for end in range(len(self.buckets)):
    start = max(0, end - span_buckets + 1)          # для end < 119 start = 0
    count = prefix[end + 1] - prefix[start]
    elapsed = min(window_sec, (end + 1) * RATE_BUCKET_SEC)   # для end < 119 это (end+1)*5
    rate = count / max(1e-9, elapsed)
```

Для любого `end < span_buckets - 1` получается `count` за всё время от старта и деление на
`(end+1)*5` — то есть **нарастающее среднее с начала прогона**, а не окно. Эти «окна» длиной
5, 10, … 595 секунд конкурируют с настоящими 600-секундными и могут победить.

Доказательство на вашем же смоуке (`runs/smoke-20261024T…`, 26 бакетов, 108 запросов):

| | значение |
|---|---|
| `requests_per_sec_max_60sec` в манифесте | **1.000** |
| максимум по полным 60-секундным окнам (12 бакетов) | **0.833** |
| откуда взялось 1.000 | `buckets[0] = 5` запросов за **первые 5 секунд** |

То есть строка «худшее 60-секундное окно» — это пятисекундное окно, завышение +20 %.
На часовом прогоне то же самое произойдёт с 10-минутной строкой: в 10a за первые 35 секунд
набирается 1.74 rps нарастающим средним, и отчёт напечатает
`пик 10-мин окна: 1.74 rps (окно 0.0–0.6 мин)` — окно, которого нет.

**Почему это не косметика.** Строка 5 приёмки сравнивает пик с 2.2 и отношение с 1.75.
Если старт получится плотнее (а на старте сходится накопленный поток детекций, и в 10a первые
пять секунд уже давали 1.0–2.4 rps), нарастающее среднее может дать 2.3–2.5 rps при том, что
**ни одно настоящее 10-минутное окно не превысило 1.8**. Прогон упадёт по строке 5 на
артефакте первых секунд, и это будет уже третий прогон подряд, красный по темпу, — с той
разницей, что теперь причина будет в измерении, а не в боте.

**Заодно про историю.** `requests_per_sec_max_60sec = 4.15` в 10a и `4.067` в run9 почти
наверняка того же происхождения: 21–22 запроса в пятисекундном бакете вокруг 25–30-й секунды
дают 4.2–4.4 rps. Эти два числа годами читались как «худшая минута» и оба раза были
пятисекундным стартовым всплеском. Их нельзя сравнивать ни с одним будущим прогоном.

## 2. Правка

В `_window_peak()` считать только полные окна:

```python
for end in range(span_buckets - 1, len(self.buckets)):
    start = end - span_buckets + 1
    count = prefix[end + 1] - prefix[start]
    rate = count / window_sec
```

Ранний выход `if end_now < window_sec: return None` оставить как есть — он честно говорит
«окно ещё не набрано» и на смоуке это единственный правильный ответ.

В `snapshot()`, в манифест, добавить `requests_per_sec_max_10min_window_kind = 'full'` (или
эквивалент), чтобы аудит видел, что окно ровно 600 с, и в отчёте печатать длину окна явно:
`пик 10-мин окна: 2.07 rps (окно 27.5–37.5 мин, 600 с), среднее 1.37, отношение 1.51`.

Тесты (минимум четыре, все воспроизводят дефект):

1. плотные первые 5 секунд (5 запросов) **не** становятся пиком 60-секундного окна;
2. плотная первая минута (150 запросов) **не** становится пиком 10-минутного окна, когда
   ни одно полное окно не превышает 1.8;
3. настоящий плотный полный участок по-прежнему выигрывает;
4. прогон короче окна → `None`, и отчёт печатает «окно ещё не набрано»;
5. (желательно) пик после правки равен `max(sum(buckets[i:i+120]))/600`, посчитанному в
   тесте руками, — то есть определение и проверка совпадают буквально.

## 3. Что сделать до запуска

1. Правка + тесты, `pytest tests -q` (351 + новые) — число назвать точно.
2. Смоук: `SMOKE OK`, в манифесте `sum(requests_per_5sec) == requests`,
   `requests_per_sec_max_60sec` равен максимуму по **полным** 12 бакетам (на прошлом смоуке
   это 0.833, а не 1.000).
3. Пересобрать `dist/`, `BUILD` = новый коммит, имя zip — новое время UTC.
4. В ответе дословно: `BUILD`, имя zip, число тестов, `requests_per_sec_max_60sec` смоука и
   максимум по полным окнам, посчитанный вами вручную.

После этого 10a′ запускается как записано в `run-logs/run10a2-1h-TEMPLATE/RUN_NOTES.md` —
команда и 14 строк приёмки там уже зафиксированы, менять их не нужно.

## 4. Чего в этой правке нет

Торговля не трогается: `fee_cover` +3.5 %, стоп −10 %, часы 5 с, 500 ₽, банк 1 500 ₽,
`MAX_POSITIONS = 3`, полосы, копии, `ENTRY_DELTA_MIN_SOL = 0.00`, `MARK_POLL_SEC = 0.25`,
`MARK_POLL_RPS_LIMIT = 2.5`, толеранс 0.75 с, расписание призрака, `RPC_MAX_CONCURRENT = 6`,
кэш чтений. Пороги приёмки не меняются: 1.8 / 2.2 или 1.75 × среднего / 429 0.5 %.
