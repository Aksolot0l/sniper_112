### B-1. Нового бандла нет в репозитории


Единственный zip в репозитории — **build `0351991`**, то есть сборка прогона №4, на две
генерации старше. Заявленного `sniper_ab_paper_local_20261023T052413Z.zip` (BUILD `5fa122b`)
в репозитории нет: он не закоммичен. При этом исторически бандлы коммитились

и его просто не выполнили.

**Следствие:** запускать на своей машине нечего. `START_*.bat/sh` и `run_local_session.py`
с правками B3 у пользователя появятся только после коммита `dist/*.zip`.

## 3. P1 — отчёт будет обманывать (не блокирует запуск, но испортить выводы успеет)

### C-1. `rocket_accounting` считает ракеты по времени удержания, а не по окну наблюдения

`portfolio_ab.py:834` берёт `peak_pct` из сделки, а это максимум **пока позиция открыта**.
У A медианное удержание — 5.1 с. На данных run6 разница четырёхкратная:

| метод | ракет ≥ +50 % | доля | точка безубыточности |
|---|---:|---:|---:|
| по `peak_pct` сделки (как реализовано) | **3 / 167** | 1.8 % | **1.34 %** |
| по наблюдениям 0…120 с (как в промпте) | **13 / 167** | 7.8 % | **6.89 %** |

Это тот же самый знаменатель, из-за которого в run6 «трейл отдаёт пик, A забирает 12 %»
оказалось артефактом. Реализация занижает ракеты в 4 раза и делает главный показатель
стратегии (доля ракет против точки безубыточности) оптимистичнее реальности в 5 раз.

**Починить:** считать по `observations.csv` (offset 0 против окна 60 с), а не по сделке.
Если оставлять по сделке — переименовать в `in_trade_peak` и в `SUMMARY.md` написать
«окно = время удержания, между армами не сравнивать».

### C-2. «Худший» шаг между метками печатает лучший

`portfolio_ab.py:2825–2839`: `'worst': round(min(values), 4)`. Для процентов SL это верно
(минимум = худший филл), для `mark_gap_ms` — наоборот. `main_ab.py:435` печатает
`худший {_money(gaps.get('worst'))}` — в смоуке вышло «медиана 5553 мс, худший 714 мс».

**Починить:** для гэпов брать `max`, либо добавить в `stats()` отдельные `worst_low` /
`worst_high`.

### C-3. Критерий «≤ 2.2 rps в любом 10-минутном окне» проверить нечем

`price.py:160` считает только среднее за прогон. В RUN_NOTES и в критериях P0 стоит окно
10 минут — метрики для него нет. Либо добавить `requests_per_sec_max_10min`
(rolling max по 600 с), либо убрать критерий из отчёта, чтобы он не висел вечно
непроверенным.

## 6. Ответ на вопрос про зипы

сборка прогона №4, она не содержит ни B3, ни P0-фиксов. Держать её в `dist/` рядом с новым

в `dist/` **ровно один** zip — текущий, а предыдущий убрать совсем (история всё равно
в git).
