# Прогон №10, этап 10a′ — 1 час, проверка пика и кэша

Отдельный каталог, отдельные заметки, отдельная страница отчёта. Данные 10a
(`run-logs/run10a-1h-20261023T182637Z`) сюда не подмешиваются: 10a′ — другой
билд (в манифесте появился `requests_per_5sec`), и суммы двух прогонов
несравнимы ни по запросам, ни по времени.

Номер прогона тот же — `run10`. Торговля не меняется ни в одном числе.

Всё, что ниже до раздела «После прогона», записано **до старта** и задним
числом не редактируется.

## 0. Команда (дословно)

```bash
DURATION_SEC=3600 RUN_NUMBER=run10 bash START_MAC_LINUX.sh \
    --run-id run10a2-1h-$(date -u +%Y%m%dT%H%M%SZ)
```

Ни одного нового `export` против `run10a-1h-20261023T182637Z`: те же книги, тот
же выход, та же каденция, то же расписание наблюдений `0,5`, тот же
`MARK_POLL_RPS_LIMIT = 2.5`, те же `ENTRY_DELTA_MIN_SOL = 0.00` /
`ENTRY_DELTA_MAX_SOL = 1.00`. Запускает пользователь, один процесс.

## 1. Что именно проверяется (до старта)

В 10a три строки приёмки были выведены, а не измерены:

1. **Пик.** `requests_per_sec_max_10min` считался в памяти, в манифест попадало
   одно число, поэтому худшее окно нельзя было ни пересчитать, ни разложить.
   Проверка: `manifest.rpc_metrics.requests_per_5sec` — массив счётчиков по
   5 с от старта (12/мин, 720/ч, 8 640/12 ч), `sum(requests_per_5sec) ==
   requests`, и `requests_per_sec_max_10min` пересчитывается из этого же массива
   независимо. В отчёте строка `пик 10-мин окна: <rps> (окно <a>–<b> мин),
   среднее <m>, отношение <r>`. **Читается третье число** — отношение.
2. **Разложение запросов.** `tools/rpc_decomposition.py` берёт суммарное число
   запросов окна из массива, вычитает посчитанные по меткам чтения кандидатов и
   получает часть опроса как разность измеренных чисел. Раньше опрос
   масштабировался линейно: на окне 21–31 мин это давало 1 030 запросов, а по
   `ticks.csv` в том же окне было 431 цикл опроса против 310 — ошибка 40 %
   уходила ровно в красную строку. Оговорки «scaled linearly» в выводе 10a′ быть
   не должно.
3. **Входные чтения.** `entry_reads_per_candidate` ≤ 1.15 — кэш `entry_reads.py`
   и правило «один батч на кандидата за цикл» проверяются числом, а не текстом.

Ни `fee_cover` +3.5 %, ни стоп −10 %, ни часы 5 с, ни ставка/банк/слоты, ни
полосы, ни копии, ни `MAX_POSITIONS`, ни расписание, ни `RPC_MAX_CONCURRENT`
в этом блоке не трогаются. Кэш чтений и правило призрака не пересматриваются —
их проверяет 10a′.

RPS «чтобы выжить» нельзя. Деньги на 10a′ не читаются: час даёт S2 CI95 ≈ ±51 ₽.
