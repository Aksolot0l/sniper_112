# Промпт Кодеру — ДОПОЛНЕНИЕ к прогону №3: банк, пополнения, стоп-лист

> Это отдельный патч **поверх** уже отправленного промпта на прогон №3. Ничего из него
> не переделывать: `delta_cap` A=2.5 / B=3.0, гейт → `shadow_gate_met`, фикс offset
> в `telemetry.py:697`, `fail_history`, MFE/MAE, CI в отчёте — всё остаётся как было.
> Здесь только учёт капитала и правила остановки. Порядок применения любой.

## 0. Зачем (факт, а не гипотеза)

Ставка фиксированная — 500 ₽ при банке 1 500 ₽. Профиль может открывать сделки, пока
накопленный PnL не ниже **−1 000 ₽** (после этого `cash < 500`, и он стоит).

- Прогон №1 закончился для A на **464.44 ₽** — до следующей сделки не хватало 36 ₽,
  при 26 сделках за 7.8 минуты.
- При средней сделке −27.29 ₽ (два прогона) пол наступает на **~37-й сделке ≈ 1.4 часа**.
- В 8-часовом прогоне это значит: A умрёт через ~1.4 ч, n(A) = 37 вместо 200, и сравнение
  армов превратится в «кто кого переживёт» вместо сравнения правил.

## 1. Правило пополнения (только бухгалтерия)

1. У каждого профиля (A, B, `shadow_*`) свой `cash`, как сейчас.
2. Если перед открытием сделки `cash < 500`, профиль **не пропускает сделку, а пополняется
   до 1 500 ₽** и открывает её.
3. Каждое пополнение пишется отдельной записью: `top_up`, `profile`, `amount_rub`,
   `cash_before`, `cash_after`, `cumulative_injected_rub`, `at_utc`, `at_trade_no`.
   В `ab_summary.json` по каждому профилю: `top_ups`, `capital_injected_rub`.
4. **Не меняется ничего, кроме этого:** ставка 500 ₽, `MAX_POSITIONS = 3`, `duplicate_symbol`,
   все входы и выходы. Пополнение не влияет ни на одно решение — только на «торговать /
   не торговать», чего без него не было бы.
5. Пополнение выполняется **только** при `cash < 500` (не «до 1500 после каждого убытка»),
   иначе счётчик пополнений перестанет быть метрикой.

## 2. Что писать в отчёт

По каждому профилю — две величины:

- `pnl_with_topups` — сумма PnL сделок, то, что нужно для сравнения правил;
- `equity_no_topups` = 1500 + cumPnL, плюс `bust_at_trade` и `bust_at_utc` — номер сделки
  и время, когда касса впервые опустилась ниже 500 ₽. Если не опускалась — `null`.

`bust_at_trade` — это и есть ответ на вопрос «а выжил бы реальный банк 1 500 ₽».
`top_ups` — вторая метрика: A при −27 ₽/сделку за 8 часов потребует ~4–5 пополнений,
B при нулевом эдже — ~9, прибыльный B — ноль.

## 3. Стоп-лист: когда прогон останавливается досрочно

Останавливать **только** по этим причинам, проверка на каждом цикле:

1. `telemetry.dropped_events > 0` или `write_errors > 0`.
2. RPC: `failed_requests / requests > 1 %` за последние 10 минут, либо `latency_p95 > 1 000 мс`
   пять минут подряд.
3. Профиль не открывает сделок 30 минут при живом потоке (`entry_state` за это окно растёт).
4. Остаток квоты Helius < 10 % или свободного места на диске < 2 ГБ.

При остановке: записать `early_stop_reason` (одна из четырёх причин + численное условие),
дописать `SUMMARY.md` и выгрузить артефакты, не обнуляя прогон.

**Не является причиной остановки:** «A ушёл в минус», «B сильно обгоняет», «слишком долго».
Остановка по PnL — это подгонка результата. Если один профиль всё же встал (например,
пополнение запрещено) — писать `bust`, продолжать вторым и сравнивать `₽/сделку` на фактических n.

## 4. Acceptance

1. Тест на синтетическом тик-потоке: просадка до cumPnL −1 200 ₽ даёт **ровно одно**
   пополнение, `cash_before < 500`, `cash_after = 1500`, сделка открывается.
2. Тест изоляции: при одинаковом тик-потоке `paper_fills` A/B совпадают с прогоном без
   пополнений — пополнение не меняет ни одной сделки, только их наличие после истощения.
3. `ab_summary.json` содержит `top_ups`, `capital_injected_rub`, `pnl_with_topups`,
   `equity_no_topups`, `bust_at_trade`, `bust_at_utc` по каждому профилю.
4. Тест стоп-листа: искусственно поднятый `dropped_events` → прогон останавливается
   с корректным `early_stop_reason`, артефакты дописаны.
5. `SUMMARY.md`: строка «банк» по каждому профилю — сколько пополнений и когда умер бы
   реальный банк 1 500 ₽.
